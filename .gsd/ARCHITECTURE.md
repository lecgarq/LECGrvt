## Overview

The LECG Revit Addin provides a comprehensive suite of utilities for architecture workflows, extending Autodesk Revit functionality. It primarily revolves around an MVVM (Model-View-ViewModel) architecture tailored for WPF (Windows Presentation Foundation) to interact with the Revit API seamlessly.

The project is structured into modular areas: 
- `LECG`: The main application orchestrating Views, ViewModels, Services, and Revit Commands.
- `LECG.Core`: Foundational types, shared algorithms, naming conventions, result encapsulation, filtering, graphics overrides, and cross-cutting concerns separated from UI logic.
- `LECG.Tests`: Xunit test project targeting `LECG.Core`.

## Components

- **Purpose:** Entry points for Revit's `IExternalCommand` interface.
- **Location:** `src/Commands`
- **Focus:** They initialize ViewModels, set up services (frequently using Dependency Injection concepts mentally if not strictly via IoC containers), and launch WPF Views.

### Views (`src/Views`)
- **Purpose:** WPF-based user interfaces.
- **Location:** `src/Views`
- **Dependencies:** Built on standard `.xaml` structures, bound to `src/ViewModels`.

### ViewModels (`src/ViewModels`)
- **Purpose:** MVVM ViewModels implementing UI logic and Command bindings.
- **Location:** `src/ViewModels`
- **Dependencies:** `CommunityToolkit.Mvvm`, Domain services (`src/Services`), Revit API context wrappers.

### Services (`src/Services`)
- **Purpose:** Heavy lifting of the application. Contains transaction handling, algorithm execution, data mapping to/from Revit, CAD manipulation, naming conventions execution, and optimization.
- **Location:** `src/Services`
- **Dependencies:** Revit API (`RevitAPI.dll`), `LECG.Core`.

### LECG.Core (`LECG.Core`)
- **Purpose:** Fundamental rules, Result envelopes, strict domain logic disconnected from WPF logic. Contains `Purge`, `Rename`, `Filtering`, `Graphics` and `Result.cs`.
- **Location:** `LECG.Core/`

## Data Flow

1. User invokes a tool within Revit via the Ribbon/Command.
2. The corresponding `IExternalCommand` (in `src/Commands/`) triggers.
3. Relevant `Service` instances are spun up and passed to a `ViewModel`. 
4. The `ViewModel` is databound to a WPF `View` shown to the user.
5. User actions relay via Commands onto the `ViewModel`.
6. `ViewModel` securely triggers data modification logic located in `Services` (which internally manage `TransactionService`).
7. Progress updates/status callbacks trigger UI feedback, and execution yields a `Result` status to the user.

## Conventions

**Naming:** C# standards, PascalCase for classes, camelCase for internal privates, explicit noun definitions for Services (e.g., `AlignEdgesBoundaryPointService`).
**Structure:** MVVM strict separation. Commands trigger Views > bound to ViewModels > invoke Services.
