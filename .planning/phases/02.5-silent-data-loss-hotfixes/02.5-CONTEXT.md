<decisions>
## Implementation Decisions

### A. Failure UX — refuse-all everywhere

- **Category Changer (Plan 2.5-2):** Refuse-all. If ANY instance has unsupported geometry (`LocationCurve`, hosted, face-hosted not handled by `SwapInstances`), abort the entire command. No partial migrations. Log every unsupported instance with element ID + reason.
- **Convert Family (Plan 2.5-3):** All-or-nothing. Partial migration failure → roll back transaction; originals untouched, new family unloaded.
- **Compact Styles (Plan 2.5-1):** When a parameter is unreadable via the locale-safe path, treat as **distinct** — never merge a style whose signature can't be fully read. Safe-by-default; may leave near-duplicates for the user to resolve manually.
- **Logging surface:** All refusals/skips go to `LogView` only. No TaskDialog popups, no end-of-run summary dialog.

### B. Convert Family — pre-flight + rollback semantics

- **Pre-flight validator** runs BEFORE any destructive op. Walks all selected instances and verifies:
  1. Original symbol's type name exists in the new family (Q-B3).
  2. Host is reachable for hosted instances (Q-B4) — fail if host deleted, in linked file, or category-mismatched.
  3. `LocationCurve` instances are handled by the migration path.
- **Symbol pick:** Match new-family type by exact name. If new family lacks that type name → fail pre-flight for that instance. **No first-symbol fallback.**
- **Host fail:** Refuse the instance at pre-flight. Per Q-B1 + Q-A1 refuse-all, any failed instance cascades to refusing the whole batch.
- **Order:** Pre-flight → load new family → migrate instances → delete originals. NEVER delete originals before new family is loaded and migrations succeed.

### C. Plan order, commits, branching

- **Execution order:** Compact Styles (2.5-1) → Category Changer (2.5-2) → Convert Family (2.5-3). Smallest-to-largest per SYNTHESIS recommendation.
- **Commits:** 3 independent commits, one per plan. Each plan self-contained; if Convert Family slips it does not block the other two from being committed.
- **Branch:** Stay on `codex/review` (matches Phase 2 pattern).
- **Release:** Wait for full Phase 2.5 completion before tagging/releasing. Single release entry covers all 3 fixes.

### D. Phase 2 interaction

- **Code work:** Phase 2.5 proceeds in parallel with Phase 2 — no file overlap, safe to start now.
- **If Phase 2 verification fails:** Pause Phase 2.5, fix Phase 2 first, then resume.
- **Verify cadence for 2.5:** All three plans verified in one Revit session at phase end (not per-plan).

### E. Test strategy

- **Bar:** Manual Revit checklist only. No unit-test harness in this phase. Test infra deferred to v1.2.
- **Checklist location:** Each plan's `SUMMARY.md` carries its own "Verification" section (matches Phase 2 pattern).
- **Fixtures:** User has real-project fixtures. Claude specifies what's needed; user supplies:
  - Spanish-locale Revit text styles (for 2.5-1 locale verification)
  - Mixed-location-type instances — `LocationCurve`, wall-hosted, face-hosted (for 2.5-2)
  - Wall-hosted family with multiple non-default type names (for 2.5-3 symbol fidelity + host restore)
- **Regression:** Phase 2 (FormulaAutoGrouping) re-verified in the same Revit session as Phase 2.5. Single verification pass covers both phases.
