# Phase 2.5 Plan 03: Convert Family Pre-flight + Load-Before-Delete Summary

**FamilyConversionService rewritten to load-before-delete with pre-flight validation, exact symbol-name matching, and hosted/curve placement overloads — eliminating five silent data-loss paths in ExecuteFamilyGroupConversion (REQ-10)**

## Accomplishments
- `FamilyInstanceData.OriginalSymbolName` captured at `Capture()` time via `instance.Symbol?.Name` — type identity preserved across the conversion boundary
- `ValidatePreFlight` runs before any transaction: checks symbol name non-null and host element reachable; throws `InvalidOperationException` if any instance fails — originals untouched
- `ExecuteFamilyGroupConversion` ordering reversed: pre-flight → LoadFamily → symbol verification → DeleteCapturedInstances → ReplaceCapturedInstances (was delete → load → place)
- `FindReplacementSymbolByName` replaces `FindReplacementSymbol`: ordinal exact-name match on `FamilySymbol.Name`; no first-symbol fallback; missing type name throws before delete
- `TryPlaceReplacementInstance` now has three branches: curve (`NewFamilyInstance(Curve, FamilySymbol, Level, StructuralType)`), hosted-point (`NewFamilyInstance(XYZ, FamilySymbol, Element, StructuralType)`), free-standing point (existing)
- Silent skip on null `LocationPoint` removed — curve-driven instances now placed instead of skipped

## Decisions Made

**Open Question 1 resolved (from RESEARCH.md):** `FamilyLoadOptionsFactory.OnFamilyFound` returns `true` with `overwriteParameterValues = true`, forcing Revit to reload the family even when live instances reference the old one. Load-before-delete is therefore safe — no fallback needed.

**Refuse-all on missing type name:** After `LoadFamily` succeeds, a `Dictionary<string, FamilySymbol>` is built for every distinct `OriginalSymbolName` in the batch. If any name is missing from the new family, an `InvalidOperationException` is thrown BEFORE `DeleteCapturedInstances` runs. Originals remain intact. The new family is left loaded in the project (acceptable: the load already completed without destructive side effects).

**Face-hosted instances — deferred:** `FamilyInstanceData` does not capture `HostFace`. Face-hosted instances cannot be detected from captured data alone at pre-flight time, so they are NOT refused. At placement they fall through to Branch 3 (free-standing). Pre-flight will NOT flag this. v1.2 should expand `FamilyInstanceData` to capture `HostFace` if face-hosted preservation is in-scope.

**No SubTransaction:** Refuse-all semantics use a single `InvalidOperationException` throw caught by the existing `IsExpectedGroupConversionException` filter. No sub-transaction needed.

## Deviations from Plan

None — plan executed exactly as written. Tasks 2 and 3 were combined into one compile-and-commit cycle as the plan explicitly recommended.

## Known Limitation: Face-Hosted Preservation

Face-hosted family instances will pass pre-flight (not detectable without `HostFace` in `FamilyInstanceData`) and will be placed at Branch 3 (free-standing, no host, no face). This is a regression for face-hosted workflows. Deferred to v1.2:
- Expand `FamilyInstanceData` to capture `Reference HostFace` + face normal
- Add Branch 0 in `TryPlaceReplacementInstance` using `NewFamilyInstance(Reference, XYZ, FamilySymbol)`
- Add pre-flight refusal if `HostFace != null && FamilyInstanceData` marks it as face-hosted
