## Summary

Three silent data-loss bugs were surfaced by the 5-plugin audit, each in a different file and touching a different Revit API surface. This research confirms the exact API facts each fix requires and documents the pitfalls that caused the original bugs.

**Plan 2.5-1** fixes locale-fragile `LookupParameter` calls in `TextStyleCompactionService.BuildSignature`. Two of the three offending lookups (`"Horizontal Alignment"`, `"Leader Arrowhead"`) have stable `BuiltInParameter` equivalents confirmed in the Revit 2024 assembly JSONL dump. The third — `"Text Orientation"` — has NO `BuiltInParameter` in `TextNoteType` context; the safe-by-default policy (treat as distinct if unreadable) covers this gracefully without requiring a string table.

**Plan 2.5-2** adds a pre-flight detect-and-refuse gate inside `SwapInstances`. Detection uses `instance.Location is LocationCurve`, `instance.Host != null`, and `instance.HostFace != null` — all confirmed as live `FamilyInstance` properties in the API. The refuse-all shape wraps the entire batch in one `Transaction` committed only after all instances are verified safe; any unsupported instance rolls back the whole thing.

**Plan 2.5-3** is the most invasive. It adds a pre-flight validator (runs before any destructive op), fixes `FindReplacementSymbol` (exact type-name match instead of `.First()`), restores host by using the `NewFamilyInstance(XYZ, FamilySymbol, Element, StructuralType)` overload with the captured `HostId` element, places `LocationCurve` instances via `NewFamilyInstance(Curve, FamilySymbol, Level, StructuralType)`, and moves deletion to AFTER `LoadFamily` succeeds.

**Primary recommendation:** For each plan, use the smallest possible diff. All three plans touch hot paths in production code. Refuse-all means a single `Transaction.RollBack()` is the failure path — do not use `SubTransaction` (Phase 2 pattern) — this phase explicitly rejects partial success.

## Architecture Patterns

### Cross-cutting: Refuse-all transaction shape

This phase uses a **single `Transaction` per command run**, committed only if all instances pass. This is the opposite of Phase 2's SubTransaction-per-parameter approach.

```csharp
// Verified pattern: TransactionService.Run wraps one transaction; throw inside = RollBack
_transactionService.Run(doc, "Swap Transplanted Instances", _ =>
{
    // Pre-flight scan (no mutations yet)
    foreach (var fi in oldInstances)
    {
        if (IsUnsupportedLocationType(fi))
        {
            // Log with element ID
            _viewModel.OnLog?.Invoke(
                $"    [REFUSED] Instance {fi.Id} unsupported location type: {DescribeLocationType(fi)}");
            throw new InvalidOperationException(
                $"Batch refused — instance {fi.Id} has unsupported location type.");
        }
    }
    // Only reached if all instances passed
    foreach (var fi in oldInstances) { /* swap */ }
});
```

The `TransactionService.RunInternal` re-throws after `RollBack` (line 136, `TransactionService.cs`), so the caller sees the exception and can log it. The VM's outer try/catch in the event handler catches it as an `IsExpectedCategoryChangerException`.

### Pattern: Safe-by-default for unreadable signature parts (Plan 2.5-1)

When a parameter is unreadable, output a sentinel value that is unique per style — not a shared fallback integer. The implementation uses `null`-tagged strings rather than `0`.

```csharp
// WRONG (current): returns 0 on null — two distinct styles share "Alignment:0"
private static int GetIntParamByName(TextNoteType type, string name) =>
    type.LookupParameter(name)?.AsInteger() ?? 0;

// CORRECT (new): returns sentinel that differs per type-id — styles never falsely collide
private static string GetStringOrSentinel(TextNoteType type, BuiltInParameter bip)
{
    Parameter? p = type.get_Parameter(bip);
    return p != null ? p.AsInteger().ToString() : $"UNREADABLE:{type.Id}";
}
```

Using `type.Id` as the sentinel ensures two types with unreadable alignment will never be considered identical.

### Pattern: Pre-flight validator before destructive ops (Plan 2.5-3)

Run a read-only scan over all captured instances before `DeleteCapturedInstances` is called. Throw (or return a failure result) if any instance fails. Because `DeleteCapturedInstances` is called in its own transaction inside `ExecuteFamilyGroupConversion`, the pre-flight check must run before that transaction starts.

```csharp
// In ExecuteFamilyGroupConversion, BEFORE the replaceInPlace block:
ValidatePreFlight(capturedInstances.CapturedData, doc);
// throws InvalidOperationException if any instance fails — caught by outer handler,
// originals untouched because delete has not yet been called
```

Pre-flight checks (per CONTEXT.md decisions):
1. Exact type-name match in new family (validate before LoadFamily if possible, or after loading in a rollback-eligible window).
2. Host reachable: `doc.GetElement(data.HostId) != null` where `data.HostId != null`.
3. LocationCurve instances detected: pre-flight accepts them (since the fix adds handling), but raises an error if the family is curve-based AND the new symbol cannot support curve placement.

## Plan 2.5-1: Compact Styles — Locale-Safe Text Style Signature

### Problem recap

`TextStyleCompactionService.BuildSignature` (line 176-178) calls:
- `GetIntParamByName(type, "Horizontal Alignment")` → uses `LookupParameter(name)` which is locale-dependent
- `GetIntParamByName(type, "Text Orientation")` → same problem
- `GetElementIdParamByName(type, "Leader Arrowhead")` → same problem

On Spanish Revit, these return `null` → all resolve to `0` / `""` → styles with different alignments/arrowheads are falsely grouped as identical → wrong rewiring.

### API facts (verified in Revit 2024 assembly JSONL)

| What code looks up | BuiltInParameter | Constant value | Notes |
|--------------------|-----------------|----------------|-------|
| `"Horizontal Alignment"` | `BuiltInParameter.TEXT_ALIGNMENT` | `-1006400` | **Use this.** Confirmed present in assembly. |
| `"Leader Arrowhead"` | `BuiltInParameter.LEADER_ARROWHEAD` | `-1006315` | **Use this.** Confirmed present. This is an `ElementId` parameter. |
| `"Text Orientation"` | **No BIP exists** | — | Not in `BuiltInParameter` enum for `TextNoteType`. Use sentinel pattern. |

Bonus: there are also `TEXT_ALIGN_HORZ` (-1006308) and `TEXT_ALIGN_VERT` (-1006309) which are distinct from `TEXT_ALIGNMENT` (-1006400). `TEXT_ALIGNMENT` is the type-level one that matches "Horizontal Alignment" in the type properties dialog; `TEXT_ALIGN_HORZ`/`TEXT_ALIGN_VERT` are instance-level overrides. For `TextNoteType` (a type element), use `TEXT_ALIGNMENT`.

### Existing codebase pattern

The existing `GetIntParam(type, BuiltInParameter.TEXT_STYLE_BOLD)` et al. use `type.get_Parameter(bip)` — this is the locale-safe path. Replicate exactly:

```csharp
// REPLACE:
int alignment = GetIntParamByName(type, "Horizontal Alignment");
int orientation = GetIntParamByName(type, "Text Orientation");
string leaderArrow = GetElementIdParamByName(type, "Leader Arrowhead");

// WITH:
int alignment = GetIntParam(type, BuiltInParameter.TEXT_ALIGNMENT);
// TEXT_ALIGNMENT returns int (TextAlignFlags enum underlying value)

string leaderArrow = GetLeaderArrowheadId(type);
// ElementId via get_Parameter(LEADER_ARROWHEAD).AsElementId()

string orientation = GetOrientationSentinel(type);
// No BIP: use safe-by-default sentinel (see below)
```

For `"Text Orientation"` — since no BIP exists, the safe-by-default policy applies: if we cannot read the value, we cannot prove two styles are visually identical, so treat them as distinct. Use a per-type sentinel so the signature is still deterministic per type:

```csharp
private static string GetOrientationSentinel(TextNoteType type)
{
    // "Text Orientation" has no BuiltInParameter in Revit 2024.
    // Safe-by-default: if unreadable, make each type unique on this axis.
    // Try LookupParameter first (works on English); if null, use type-unique sentinel.
    Parameter? p = type.LookupParameter("Text Orientation");
    if (p != null) return p.AsInteger().ToString(CultureInfo.InvariantCulture);
    return $"ORIENTATION_UNREADABLE:{type.Id}";
}
```

This satisfies REQ-08: on Spanish Revit, two types whose orientation differs (or is unknown) will never be falsely merged. On English Revit, it works as before.

### Methods to change in `TextStyleCompactionService`

- `GetIntParamByName` — keep for orientation sentinel, but the main call for alignment switches to `GetIntParam`.
- `GetElementIdParamByName` — keep for the sentinel fallback, but the main arrowhead call switches to `GetElementIdParam(type, BuiltInParameter.LEADER_ARROWHEAD)`.
- Add `GetElementIdParam(TextNoteType type, BuiltInParameter param)` helper (same pattern as `GetIntParam`).
- Add `GetOrientationSentinel(TextNoteType type)` helper (described above).

### Don't hand-roll

Do NOT build a locale string-lookup table mapping "Horizontal Alignment" → "Alineación horizontal" etc. The `BuiltInParameter` approach is the correct Revit pattern and is already used for all other signature parameters in the same file.

## Plan 2.5-2: Category Changer — Refuse Unsupported Location Types

### Problem recap

`SwapInstances` (CategoryChangerCommand.cs line 190) does:
```csharp
if (oldFi.Location is not LocationPoint locationPoint)
{
    _viewModel.OnLog?.Invoke($"    [SKIP] Instance {oldFi.Id} has no point-based location.");
    continue;  // SILENT SKIP — old family instance still exists, new one not placed
}
```

The `continue` means the old instance is never deleted (`doc.Delete(oldFi.Id)` comes later inside the same `foreach`) — so the original remains with the old family while the user sees `[SUCCESS]`. This is the data corruption.

### API facts (verified in Revit 2024 JSONL)

| Detection | API | Notes |
|-----------|-----|-------|
| Point-based instance | `fi.Location is LocationPoint` | Current code, correct |
| Curve-based instance | `fi.Location is LocationCurve` | `LocationCurve` is a subclass of `Location` |
| Hosted (wall/slab host) | `fi.Host != null` | `FamilyInstance.Host` returns `Element?` — null if free-standing |
| Face-hosted | `fi.HostFace != null` | `FamilyInstance.HostFace` returns `Reference?` — non-null for face-hosted |
| Free-standing point | `fi.Location is LocationPoint && fi.Host == null && fi.HostFace == null` | Safe to swap with current code |

**Important:** A wall-hosted instance (`fi.Host != null`) also has `Location is LocationPoint`. Do not use `LocationPoint` as a "safe" proxy — check `Host` and `HostFace` separately.

### Refuse-all shape for `SwapInstances`

The decision (CONTEXT.md §A) is: if any instance in the batch has an unsupported type, abort the entire swap. No partial success.

The entire `SwapInstances` is already wrapped in `_transactionService.Run(...)`. The pattern is:

```csharp
private void SwapInstances(Family oldFamily, Family newFamily)
{
    // ... (existing setup: get newSymbol, collect oldInstances) ...

    _transactionService.Run(doc, "Swap Transplanted Instances", _ =>
    {
        // PRE-FLIGHT: check all instances before any mutation
        foreach (var fi in oldInstances)
        {
            string? reason = GetUnsupportedReason(fi);
            if (reason != null)
            {
                _viewModel.OnLog?.Invoke(
                    $"    [REFUSED] Batch aborted — instance {fi.Id} ({fi.Name}): {reason}");
                throw new InvalidOperationException(
                    $"SwapInstances refused: instance {fi.Id} has unsupported location type ({reason}).");
                // TransactionService.RunInternal catches and rolls back
            }
        }

        // All instances cleared — proceed with swap
        if (!newSymbol.IsActive) newSymbol.Activate();
        foreach (var fi in oldInstances)
        {
            // ... existing point-based swap logic ...
        }
    });
}

private static string? GetUnsupportedReason(FamilyInstance fi)
{
    if (fi.Location is LocationCurve)
        return "LocationCurve (line/curve-driven family)";
    if (fi.Host != null)
        return $"hosted on element {fi.Host.Id}";
    if (fi.HostFace != null)
        return "face-hosted";
    if (fi.Location is not LocationPoint)
        return "unknown location type (not LocationPoint)";
    return null; // safe to swap
}
```

The `InvalidOperationException` thrown inside `_transactionService.Run` causes `RunInternal` to call `transaction.RollBack()` and re-throw. The caller (`Execute` in `CategoryChangerEventHandler`) catches it via `IsExpectedCategoryChangerException` (which includes `InvalidOperationException`).

**Log every refused instance with element ID and reason before throwing** — the throw stops the loop, but by logging first the user can see all problems (or at least the first one).

### What to log vs throw

Per CONTEXT.md §A: "Log every unsupported instance with element ID + reason." Because the loop throws on the first unsupported instance (all-or-nothing), the log will capture that instance. If you want to log ALL unsupported instances before throwing, do a separate scan-and-log pass before the mutation pass:

```csharp
// Pass 1: Scan and log all problems
bool hasUnsupported = false;
foreach (var fi in oldInstances)
{
    string? reason = GetUnsupportedReason(fi);
    if (reason != null)
    {
        _viewModel.OnLog?.Invoke($"    [UNSUPPORTED] {fi.Id}: {reason}");
        hasUnsupported = true;
    }
}
if (hasUnsupported)
{
    throw new InvalidOperationException("SwapInstances refused — see log for unsupported instances.");
}
// Pass 2: swap (only reached if all instances are safe)
```

This gives the user a full picture before rollback, which is more useful diagnostically.

### Don't hand-roll

Do NOT re-implement the `LocationCurve` placement path. The decision is to refuse-all when unsupported types are present. The cursor "What about the future?" — the `LocationCurve` placement overload exists (`NewFamilyInstance(Curve, FamilySymbol, Level, StructuralType)`) but adding it is deferred to v1.2 per CONTEXT.md.

## Plan 2.5-3: Convert Family — Pre-flight, Host Restore, Curve Preserve, Exact Symbol Match

### Five bugs to fix

1. **`FindReplacementSymbol` picks first symbol** (FamilyConversionService.cs line 259)
2. **`HostId` captured but never used in `Apply`** (FamilyInstanceData.cs)
3. **`LocationCurve` captured but never placed** (FamilyConversionService.cs line 284)
4. **Originals deleted before new family loads** (ExecuteFamilyGroupConversion lines 144-147 precede Execute)
5. **No pre-flight validation** (any of the above can cause silent data loss)

### Bug 1: FindReplacementSymbol — exact name match

Current code (line 259):
```csharp
return doc.GetElement(symbolIds.First()) as FamilySymbol;
```

Fix: match by the captured symbol name. `FamilyInstanceData` does not currently capture the original type name — add `OriginalSymbolName` to `FamilyInstanceData.Capture`:

```csharp
// In FamilyInstanceData.Capture():
data.OriginalSymbolName = instance.Symbol?.Name;
```

Then `FindReplacementSymbol` takes the name as a parameter:

```csharp
private static FamilySymbol? FindReplacementSymbolByName(Document doc, string familyName, string symbolName)
{
    Family? newFamily = new FilteredElementCollector(doc)
        .OfClass(typeof(Family))
        .Cast<Family>()
        .FirstOrDefault(f => f.Name == familyName);
    if (newFamily == null) return null;

    foreach (ElementId id in newFamily.GetFamilySymbolIds())
    {
        if (doc.GetElement(id) is FamilySymbol sym && sym.Name == symbolName)
            return sym;
    }
    return null; // symbol name not found — caller must fail pre-flight
}
```

If this returns `null`, pre-flight fails for that instance (per CONTEXT.md §B: "No first-symbol fallback").

### Bug 2: HostId restoration — correct NewFamilyInstance overload

`FamilyInstanceData.HostId` is already captured (line 18 of FamilyInstanceData.cs). The missing piece is using it during placement.

**Confirmed overloads in Revit 2024 assembly:**
- `NewFamilyInstance(XYZ, FamilySymbol, Element, StructuralType)` — places on a host element (wall, floor, etc.)
- `NewFamilyInstance(XYZ, FamilySymbol, Element, Level, StructuralType)` — places on a host with an explicit level

```csharp
// In ReplaceCapturedInstances / TryPlaceReplacementInstance:
if (data.HostId != null)
{
    Element? host = doc.GetElement(data.HostId);
    if (host != null)
    {
        // Hosted placement — preserves host relationship
        return doc.Create.NewFamilyInstance(
            data.LocationPoint,
            newSymbol,
            host,
            StructuralType.NonStructural);
    }
    // host gone — should have been caught by pre-flight
    Logger.Instance.LogWarning($"[FamilyConversionService] Host {data.HostId} not found at placement time.");
    return null;
}
```

**Critical pitfall:** The host element (wall/floor) must still exist in the document at placement time. Pre-flight must verify `doc.GetElement(data.HostId) != null` for every hosted instance.

### Bug 3: LocationCurve placement — correct NewFamilyInstance overload

`FamilyInstanceData.LocationCurve` is already captured (line 40). The missing piece is using it.

**Confirmed overloads:**
- `NewFamilyInstance(Curve, FamilySymbol, Level, StructuralType)` — places along a curve (e.g., beam, structural framing)

```csharp
if (data.LocationCurve != null)
{
    Level? lev = ResolvePlacementLevel(doc, data.LevelId);
    if (lev == null)
    {
        Logger.Instance.LogWarning($"[FamilyConversionService] Cannot place curve instance — no valid level.");
        return null;
    }
    return doc.Create.NewFamilyInstance(
        data.LocationCurve,
        newSymbol,
        lev,
        StructuralType.NonStructural);
}
```

**Pre-flight implication:** Curve-based instances are now handled — they do NOT trigger a refusal. Pre-flight only refuses instances whose host is unreachable (null element ID, linked file element, etc.).

### Bug 4: Load-before-delete ordering

Current code in `ExecuteFamilyGroupConversion` (lines 143-149):
```
if (replaceInPlace)
{
    DeleteCapturedInstances(doc, capturedInstances.InstanceIds); // BUG: runs first
}
(targetFamilyDoc, tempFamilyPath) = _familyConversionExecutionService.Execute(...); // LoadFamily inside
```

Fix: move delete to after Execute succeeds and pre-flight passes:

```
// NEW ORDER:
// 1. Pre-flight (read-only)
ValidatePreFlight(capturedInstances, doc, targetFamilyName);  // throws if fails

// 2. Execute (creates + loads new family)
(targetFamilyDoc, tempFamilyPath) = _familyConversionExecutionService.Execute(...);
if (targetFamilyDoc == null) throw new InvalidOperationException("Family load failed");

// 3. Verify replacement symbol exists by name
FamilySymbol? newSymbol = FindReplacementSymbolByName(doc, targetFamilyName, capturedInstances.OriginalSymbolName);
if (newSymbol == null) throw new InvalidOperationException($"New family lacks type '{capturedInstances.OriginalSymbolName}'");

// 4. ONLY NOW: delete originals (they are locked by Revit until here)
if (replaceInPlace)
{
    DeleteCapturedInstances(doc, capturedInstances.InstanceIds);
}

// 5. Replace
ReplaceCapturedInstances(doc, newSymbol, capturedInstances.CapturedData, ...);
```

**Note on Revit's delete-before-load requirement:** The current code deletes first because Revit refuses to `LoadFamily` (overwrite) while instances reference the family. This is real and must be preserved. The fix is to use the `IFamilyLoadOptions.OnFamilyFound` callback to force overwrite — the `FamilyLoadOptionsFactory` already creates a load options object with override enabled. With overwrite forced, the family definition can be replaced even with live instances. Then deletion happens after load succeeds.

This means the fixed sequence is:
1. Pre-flight
2. `_familyConversionExecutionService.Execute` — internally calls `doc.LoadFamily(path, options, out family)` with `IFamilyLoadOptions.OnFamilyFound` returning `familyInUse = true, overwriteParameterValues = true`
3. Verify symbol
4. Delete originals (now the loaded family is in the doc — old instances point to old definition, which is now replaced by the new one; deleting them is safe)
5. Place new instances

**Verify the existing `FamilyLoadOptionsFactory` sets overwrite = true.** If it does, step 2 succeeds with live instances. If not, the delete-first ordering must remain but must be conditional on `LoadFamily` success. Check `FamilyProjectLoadService.Load` and `FamilyLoadOptionsFactory`.

### Bug 5: Pre-flight validator

Pre-flight must run synchronously, read-only, before any transaction:

```csharp
private static void ValidatePreFlight(
    CapturedFamilyInstances captured,
    Document doc,
    string targetFamilyName)
{
    var failures = new List<string>();

    // Check 1: Every hosted instance's host is reachable
    foreach (FamilyInstanceData data in captured.CapturedData)
    {
        if (data.HostId != null && doc.GetElement(data.HostId) == null)
            failures.Add($"Instance at {data.LocationPoint}: host {data.HostId} not found in document");
    }

    // Check 2: OriginalSymbolName — not null (captured from live instance, should never be null)
    // The exact-name check against the new family can only be done AFTER LoadFamily.
    // Pre-flight for symbol match is done post-load (see Bug 4 step 3).

    if (failures.Count > 0)
    {
        foreach (string f in failures)
            Logger.Instance.Log($"[PRE-FLIGHT] {f}");
        throw new InvalidOperationException(
            $"Pre-flight failed for family conversion ({failures.Count} issue(s)). Originals untouched.");
    }
}
```

Pre-flight cannot check the symbol name against the new family before loading, because the family isn't in the document yet. The symbol-name check happens after LoadFamily (step 3 in the ordering above). If it fails there, the originals have not been deleted yet (per the new ordering), so rollback is clean.

**Where to put pre-flight:** Place it in `FamilyConversionService.ExecuteFamilyGroupConversion` as a private static method. No new service class needed (CONTEXT.md §C leaves this to Claude's discretion; simplest is inline in the same class).

## Common Pitfalls

### Pitfall 1: `instance.Host` is non-null for wall-hosted, but `Location` is still `LocationPoint`

**What goes wrong:** A door in a wall has `Location is LocationPoint` (the insertion point). `Host` is the wall. Checking only `Location is LocationPoint` makes the instance look like a free-standing point instance — but placing it without the `Element host` overload produces a floating door with no wall relationship.

**How to avoid:** Always check `fi.Host != null` and `fi.HostFace != null` as separate guards before deciding the swap is safe.

**In this phase:** For Plan 2.5-2, this means wall-hosted families are in the unsupported set (refuse-all). For Plan 2.5-3, they are supported (use host overload) but require a reachable host element.

### Pitfall 2: `Document.LoadFamily` with overwrite — return semantics

**What goes wrong:** `doc.LoadFamily(path, options, out Family family)` returns `bool` (whether the load occurred) and sets `family` to `null` if the family was found but **not reloaded** (because `IFamilyLoadOptions.OnFamilyFound` returned `overwrite = false`). If `family == null` after a successful `bool == true` return, the family in the document is the OLD definition, not the new one. Code that checks `family == null` to detect failure will be wrong in this case.

**Confirmed signatures from Revit 2024 assembly:**
- `Document.LoadFamily(string, IFamilyLoadOptions, out Family)` — returns `bool`; `out family` is the loaded family or null
- `Document.LoadFamily(Document, IFamilyLoadOptions)` — returns `bool`; used for loading from another open doc

The current `FamilyProjectLoadService.Load` uses `doc.LoadFamily(tempFamilyPath, options, out loadedFamily)` and checks `loadedFamily != null`. This is correctly coded. The risk is if `IFamilyLoadOptions.OnFamilyFound` has `overwrite = false` — then `loadedFamily` will be null and the old definition persists. **Verify** `FamilyLoadOptionsFactory.Create()` sets `overwrite = true`.

**How to avoid:** After `LoadFamily`, check that the family in the document matches the expected definition (by querying it from `FilteredElementCollector`), not just that the out-param is non-null.

### Pitfall 3: `FamilyInstance.Host` vs `FamilyInstance.HostFace` — they mean different things

**What goes wrong:** A face-hosted element (furniture placed on a slanted surface) has `HostFace` non-null, but `Host` may also be non-null (the wall or generic model the face belongs to). Using only `Host` misses the face-reference required to restore the exact placement.

**For Plan 2.5-2 (refuse-all):** Check both. If either is non-null → unsupported.
**For Plan 2.5-3:** The current `FamilyInstanceData.Capture` stores `HostId = instance.Host?.Id` but does not store `HostFace`. For Phase 2.5, face-hosted instances are refused at pre-flight in Plan 2.5-3 (their host is a face reference, not an `Element` reachable by `ElementId`). This is acceptable given the scope.

### Pitfall 4: BIP `TEXT_ALIGNMENT` vs `TEXT_ALIGN_HORZ`

**What goes wrong:** The Revit API has three related BIPs:
- `TEXT_ALIGNMENT` (-1006400) — a type-level parameter on `TextNoteType`
- `TEXT_ALIGN_HORZ` (-1006308) — an instance-level override on `TextNote`
- `TEXT_ALIGN_VERT` (-1006309) — an instance-level override on `TextNote`

For the compaction signature, we want the **type** parameter, not the instance override. Use `TEXT_ALIGNMENT` on `TextNoteType`. Using `TEXT_ALIGN_HORZ` on a type element will return null (wrong).

### Pitfall 5: Deleting originals before `LoadFamily` — why the current code does it

The Revit API will sometimes refuse `LoadFamily` (overwrite) while live instances reference the family, throwing `Autodesk.Revit.Exceptions.InvalidOperationException`. The current code works around this by deleting first. The correct fix is to use `IFamilyLoadOptions.OnFamilyFound` with `overwrite = true`, which signals Revit to replace the definition even with live instances. **Do not remove the delete-first logic without first confirming the load options factory forces overwrite.**

### Pitfall 6: `TransactionService.RunInternal` throws on RolledBack commit

If `transaction.Commit()` returns `TransactionStatus.RolledBack`, `RunInternal` throws `InvalidOperationException("Transaction '{name}' was rolled back by Revit due to element errors.")`. This is a different path than an explicit throw inside the action. Both result in the action being aborted, but the exception message differs. The caller's `IsExpectedCategoryChangerException` covers `InvalidOperationException`, so this is handled. Be aware that Revit-initiated rollbacks produce this exception — it is not a code bug.

private static FamilySymbol? FindReplacementSymbolByName(
    Document doc, string familyName, string? symbolName)
{
    if (string.IsNullOrEmpty(symbolName)) return null;

    Family? fam = new FilteredElementCollector(doc)
        .OfClass(typeof(Family))
        .Cast<Family>()
        .FirstOrDefault(f => f.Name == familyName);
    if (fam == null) return null;

        if (doc.GetElement(id) is FamilySymbol sym
            && string.Equals(sym.Name, symbolName, StringComparison.Ordinal))
            return sym;
    }
    return null; // name not found — pre-flight should have caught this
}

## Open Questions

1. **Does `FamilyLoadOptionsFactory.Create()` force overwrite?**
   - What we know: `FamilyProjectLoadService.Load` uses it; if it does NOT set `overwrite = true`, then `LoadFamily` may fail when live instances exist, making the delete-first ordering necessary.
   - What's unclear: The factory source was not read in this research pass (`FamilyLoadOptionsFactory.cs` is a 29-LOC wrapper).
   - Recommendation: Read `FamilyLoadOptionsFactory.cs` at plan-write time. If `OnFamilyFound` returns `overwrite = true`, the new ordering (load first, delete second) works. If not, keep delete-first but gate it on a successful `LoadFamily` call (with a null-check on the out param).

2. **Does `NewFamilyInstance(XYZ, FamilySymbol, Element, StructuralType)` work for all host types?**
   - What we know: Confirmed as a valid overload in the Revit 2024 assembly.
   - What's unclear: Whether it works for floor-hosted and ceiling-hosted in addition to wall-hosted.
   - Recommendation: Log a warning if placement returns null; the pre-flight check (host exists) reduces the failure surface to cases where the host geometry changed between capture and placement.

3. **Is `"Text Orientation"` a real parameter on `TextNoteType` in some Revit versions?**
   - What we know: No BIP exists for it. The current `LookupParameter("Text Orientation")` returns null on localized installs but may work on English installs.
   - Recommendation: The sentinel approach handles this: try `LookupParameter` first (returns an integer on English), fall back to per-type sentinel. This is safe on both locales.
