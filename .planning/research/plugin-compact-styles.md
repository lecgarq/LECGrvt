# Plugin Audit: Compacting Styles

## What it does (one paragraph)

Compacting Styles is a maintenance command that walks a Revit project's style catalog (Line Patterns, Fill Patterns, Text Note Types, and Line Styles), groups graphically identical duplicates by a string signature, creates a single canonical replacement (or picks a "survivor" for line styles), rewires every reachable reference (parameters with `StorageType.ElementId`, category projection/cut overrides, view category and view filter overrides, material fill-pattern slots, `FilledRegionType` slots, and `TextNote.GetTypeId`), then deletes the now-orphaned originals. Line patterns additionally get a "rename pass" that pushes every remaining pattern toward a semantic name produced by `LinePatternNamingPolicy`. The whole pipeline is run from a single command, in four sequential transactions, with a confirm dialog up front, a non-modal `LogView` window for output, and a coarse progress bar.

## Architecture map

- `src/Commands/CompactingStylesCommand.cs:14` — entry point; `RevitCommand` subclass with `TransactionMode.Manual` and `TransactionName => null` (each scope opens its own transaction).
- Confirm UX: `CompactingStylesCommand.cs:101` → `LecgDialog.Confirm` (`src/Views/Base/LecgDialog.cs:24`).
- Log/progress UI: inherited `RevitCommand.ShowLogWindow` (`src/Core/RevitCommand.cs:70`) opens `Views/LogView` bound to `ViewModels/LogViewModel`. Progress is throttled in `RevitCommand.ShouldPublishProgress` (`src/Core/RevitCommand.cs:127`).
- Transactions: `ITransactionService.RunWithWarningHandler` (`src/Services/Infrastructure/TransactionService.cs:93`) wraps each scope; failure handler is `SafeFailureHandler` (`src/Core/SafeFailureHandler.cs:12`) which deletes warnings and rolls back on errors.
- Shared context: `CompactingStylesContext.Create` (`src/Services/PurgeAndCompaction/CompactingStylesContext.cs:69`) — collects all type elements (instances are intentionally skipped), supported views, all categories + flattened sub-categories, materials, filled-region types, text notes, and a parameter index keyed by referenced `ElementId`.
- Shared rewire/delete plumbing: `CompactionSharedHelper` (`src/Services/PurgeAndCompaction/CompactionSharedHelper.cs:8`) — parameter rewiring, view category/filter override indexing + rewiring, canonical name allocation, safe delete.
- Per-scope services (all `AddSingleton` in `src/Core/Bootstrapper.cs:95-98`):
  - `LinePatternCompactionService` (`src/Services/PurgeAndCompaction/LinePatternCompactionService.cs:13`) — 826 lines.
  - `FillPatternCompactionService` (`src/Services/PurgeAndCompaction/FillPatternCompactionService.cs:13`) — 619 lines.
  - `TextStyleCompactionService` (`src/Services/PurgeAndCompaction/TextStyleCompactionService.cs:12`) — 351 lines.
  - `LineStyleCompactionService` (`src/Services/PurgeAndCompaction/LineStyleCompactionService.cs:11`) — 268 lines.
- Result models (parallel, no shared base): `LinePatternCompactionResult`, `FillPatternCompactionResult`, `TextStyleCompactionResult`, `LineStyleCompactionResult` in `src/Models/`.
- Progress reporter: `RevitCommandProgressReporter` (`src/Services/Infrastructure/RevitCommandProgressReporter.cs:6`) — note that `LogWarning`/`LogError` collapse to plain `Log` (no severity).

There is no dedicated `CompactingStylesView`. The command does NOT reuse `PurgeView` either — it goes straight from a single confirm dialog into execution. `PurgeView` is exclusive to `PurgeCommand`.

## Findings by axis

### Functionality

- **No scope toggles.** All four scopes always run; there is no UI to disable Text Styles, skip Line Styles, etc. (`CompactingStylesCommand.cs:36-94`). Compare with `PurgeCommand` which has a 13-toggle dialog. For a destructive operation this is a real gap.
- **No dry-run / preview.** The dialog text says "creates new canonical definitions, rewires reachable references, and deletes redundant originals" — and there is zero way to inspect what will happen before it happens.
- **Line Patterns "rename pass" is unbounded and silent in scope.** `RenameToSemanticNames` (`LinePatternCompactionService.cs:512`) iterates *every* remaining `LinePatternElement` in the document — including ones the user never asked to touch — and renames them to `LECG-…` semantic names if the family/segment combo matches `LinePatternNamingPolicy`. This is a side-effect the confirm dialog does not mention. It runs even when no duplicates were found (line 62 is outside the `if (duplicateGroups.Count > 0)` block).
- **`existingNames` reservation may be incorrect after rename pass collisions.** When `RenameToSemanticNames` hits an `existingNames.Contains(preferredName)` it just `continue`s (`LinePatternCompactionService.cs:557`) — silently leaving the pattern at its non-semantic name with no log entry.
- **Text styles: default type is excluded but not its descendants.** `CollectCandidates` only excludes `defaultTypeId` (`TextStyleCompactionService.cs:153`). If the user has duplicates of the default text type, the default itself is exempt but a duplicate of it would become canonical, and other elements rewired to the canonical — possibly leaving the default unused but un-deleted.
- **Text style signature is fragile.** `BuildSignature` mixes `BuiltInParameter` lookups with hard-coded English `LookupParameter("Horizontal Alignment")` / `LookupParameter("Text Orientation")` / `LookupParameter("Leader Arrowhead")` (`TextStyleCompactionService.cs:176-178`). On a non-English Revit install these return `null` and collapse to `0` / `""`, so two visually different styles can collide under one signature → wrong rewiring. This is a correctness bug for localized projects.
- **Text styles never write back to `Element.Name` or color the canonical with a meaningful label**, but the canonical is created with `seed.Duplicate(canonicalName)` using `LECG-TT-001` etc. There is no semantic rename pass for text types (asymmetric with line patterns).
- **Line Styles: `CurveElement` rewiring is full-document and silent on lookup.** `RewireCurveElements` (`LineStyleCompactionService.cs:215`) opens a fresh `FilteredElementCollector(doc).OfClass(typeof(CurveElement))` *per source candidate* (called inside the per-original loop in `RewireReferences` at line 200, which is itself called inside the per-candidate loop at line 61). For a group of N duplicates that is N `CurveElement` collector scans across the entire model. See the Performance section.
- **Line styles never index `GraphicsStyle` references in OverrideGraphicSettings.** Categories' line styles are reachable through the subcategory; but view-level overrides that pin a specific `GraphicsStyle` (e.g. via filter overrides on the line subcategory) are not handled — only line *patterns* go through the view-override indexes. This may leave dangling references after deletion, surfacing as `BlockedDeletions`.
- **Line styles "PickSurvivor" is shortest-name-wins** (`LineStyleCompactionService.cs:175`). That is arbitrary and irreversible — `"M_Hidden"` beats `"Hidden Lines"` simply because of length. There is no policy hook (e.g., prefer non-imported, prefer existing user style, prefer pattern with semantic name).
- **Fill patterns: no fallback if create-canonical fails.** `LinePatternCompactionService.CompactDuplicateGroup` has a fallback using an existing candidate (`LinePatternCompactionService.cs:174-201`). `FillPatternCompactionService` just `continue`s to next group on creation failure (`FillPatternCompactionService.cs:67-73`), losing the entire group's compaction opportunity.
- **No idempotence test.** Re-running the command after a successful compaction will re-create more `LECG-…` patterns from any straggler duplicates, but the rename pass already named everything semantically. Names accumulate (`LECG-LP-001`, then `LECG-LP-002` next run, etc.) because `existingNames` is rebuilt each run from the live document and `nextCanonicalIndex` resets to 1 — actual collisions just bump the counter forward.
- **Dead/unused legacy entry points.** Every service exposes both an `IProgressReporter` overload and a legacy `(Action<string>, Action<double,string>)` overload (e.g. `LinePatternCompactionService.cs:18`, `FillPatternCompactionService.cs:17`, etc.). The command only ever uses the `IProgressReporter` form. The legacy overloads + `LegacyProgressReporter` adapter exist solely for callers that don't exist.
- **`RunWithWarningHandler` re-applies a warning swallower on top of `SafeFailureHandler`.** The command passes `SafeFailureHandler` explicitly (`CompactingStylesCommand.cs:34, 39`), but `TransactionService.RunWithWarningHandler` (`TransactionService.cs:93`) defaults to `WarningSwallower` if you pass null and uses your handler when you pass one — so this is fine, just confusing naming. (`SafeFailureHandler` itself rolls back on errors; `WarningSwallower` likely auto-deletes elements which is what they're avoiding.)
- **`CompactingStylesContext` is rebuilt 4 times.** Each scope calls `CompactingStylesContext.Create` inside its transaction (`CompactingStylesCommand.cs:41, 56, 71, 86`). The parameter index is the expensive part and it's recomputed from scratch every scope. See Performance.

### Error handling

- **Top-level: command exceptions caught in `RevitCommand.Execute`** (`src/Core/RevitCommand.cs:46`) — message is logged + log window forced open. That part is solid.
- **Transaction-level: `RunInternal` throws on `RolledBack` commit** (`TransactionService.cs:122-126`). If scope 1 (Line Patterns) throws, scopes 2-4 are skipped — but they would silently leak progress (`UpdateProgress(25, "Compacting Fill Patterns...")` never fires). The user sees partial work plus an error message; no recovery hint, no "you can re-run safely" note.
- **Per-element exception swallowing is pervasive but inconsistent.**
  - `CompactionSharedHelper.RewireParameterReferencesFromIndex` (`CompactionSharedHelper.cs:42-51`) — three almost-identical catch blocks per parameter, each logging through the global `Logger` but **not** through the command's `IProgressReporter`. So those messages never reach the visible LogView; they go to the file/console sink only.
  - `LineStyleCompactionService.CollectCandidates` (`LineStyleCompactionService.cs:151-154`) — bare `catch { }` with no logging at all. Subcategories that fail to read are silently dropped from compaction.
  - `LineStyleCompactionService.RewireCurveElements` (`LineStyleCompactionService.cs:232-234`) — bare `catch { }`. A throwing curve is silently un-rewired; the count won't reflect it.
  - `LinePatternCompactionService.TryRenamePattern` (`LinePatternCompactionService.cs:472-475`) — bare `catch { return false; }`. No reason logged.
  - `LinePatternCompactionService.RenameToSemanticNames` (`LinePatternCompactionService.cs:571-574`) — bare `catch { /* Revit may reject the rename */ }`. Comment is honest, behaviour is silent.
- **`TextStyleCompactionService` does not call `Document.Regenerate()` between phase 1 (rewire) and phase 2 (delete)** despite the comment `// Step 3: Two-phase approach — rewire all groups, then single Regenerate + delete` (`TextStyleCompactionService.cs:66`). The comment promises a Regenerate that is never invoked. If the engine needs that flush before delete-eligibility is established, deletes may fail and end up in `BlockedDeletions` for no apparent reason. Either the comment is stale or the call was lost.
- **No explicit handling of `Document.Delete` returning multiple ids.** `CompactionSharedHelper.TryDeleteElement` (`CompactionSharedHelper.cs:70`) returns `true` if `>0` ids were deleted but never logs the cascading deletes. If deleting a fill pattern cascades into anything unexpected, nobody knows.
- **`SafeFailureHandler` deletes ALL warnings.** Including potentially informative ones. The command would benefit from at least logging which warnings were swallowed during each scope.

### Performance

- **`CompactingStylesContext` is built 4×.** Type-element collector + parameter index built fresh for every scope (`CompactingStylesCommand.cs:41, 56, 71, 86` → `CompactingStylesContext.Create`). The parameter index walks every type element's full `Parameters` collection — that's the single most expensive thing the command does. The context could trivially be built once before the first scope and passed in (transactions don't invalidate it for read-only purposes; element ids stay stable across rewires within the same session).
- **`BuildViewCategoryOverrideIndex` is O(views × all-categories-and-subcategories)** for each scope (`CompactionSharedHelper.cs:111-147`, `IndexCategoryHierarchyOverrides` at line 254). For a model with 2,000 views and 1,000 (cat + subcat) entries that is 2M `view.GetCategoryOverrides` calls — per scope, run twice (once for line patterns, once for fill patterns). This is the dominant cost on large models.
- **`LineStyleCompactionService.RewireCurveElements` re-scans the whole document.** Called from `RewireReferences` at `LineStyleCompactionService.cs:200`, which is inside the per-original loop at line 61. For a `LinesCategory` with a duplicate group of N styles, the entire `CurveElement` set is collected N-1 times. Pre-building one curve→subcategoryId index would be a 10-100× win.
- **`existingNames` `HashSet<string>` for line patterns is allocated twice.** Once in `Compact` itself (`LinePatternCompactionService.cs:44`) and again — implicitly — by `RenameToSemanticNames`'s logic which also references the same set. Minor but worth tightening.
- **`group.Count()` called inside loops.** `TextStyleCompactionService.cs:110, 112` calls `group.Count()` repeatedly inside the per-group loop on an `IGrouping`. Multi-enumeration of a grouping is O(group size). Not catastrophic since groups are small, but symptomatic of "throwing LINQ at it."
- **No batching across scopes.** Four separate transactions = four commit-undo records. For large models the user gets four undo entries to manage.
- **Materials loop iterates every material** even when the group's source ids are tiny. `BuildMaterialPatternIndex` (`FillPatternCompactionService.cs:303-322`) checks `sourceIds.Contains(patternId)` for every material × 4 slots, which is fine (HashSet lookup), but the per-source rewire (`RewireMaterialReferencesFromIndex`) re-reads `material.SurfaceForegroundPatternId` etc. for confirmation. Acceptable, just dense.

### UX / UI

- **Single confirm dialog → straight into execution.** `LecgDialog.Confirm` (`CompactingStylesCommand.cs:103`) — message says what will happen but offers no scope toggles, no "preview", no "abort if more than X items affected" safety. The user has to commit to all four scopes blind.
- **Progress bar is jumpy and lies.** Phase boundaries are hard-coded at 5/25/50/75/100 (`CompactingStylesCommand.cs:37, 52, 67, 82`), and within a phase each service emits its own 0-100% mapped onto the whole bar via `Math.Round((groupIndex + originalIndex/groupSize) / groupCount * 100)` which **overwrites** the phase boundaries (e.g. `progressCallback?.Invoke(100, "Line pattern compaction complete")` at `LinePatternCompactionService.cs:64` jumps from 5% → 100% → 25% on the next scope). Bar will visibly jitter back and forth.
- **No cancel button.** `LogView` is non-modal but there is no `CancellationToken` plumbed through any service. A user mid-run on a 30-minute project has no recourse besides killing Revit.
- **LogView is `Topmost = true`** (`RevitCommand.cs:80`) — locks itself over every other Revit window. Annoying when the user wants to glance at the project.
- **No completion summary dialog.** The final `=== COMPACTING COMPLETE ===` is just a log line. No modal confirming "X duplicates removed; Y references rewired; click here to undo." The user has to scroll the log.
- **No undo guidance.** Each scope is a separate transaction → 4 undos required to reverse. The command does not warn about this or offer a "group all under one transaction" option. (Doing so would be feasible by switching to `Transaction` + `SubTransaction`, but the current design forecloses it.)
- **Confirm dialog detail copy is generic and slightly inaccurate.** "rewires reachable references, and deletes redundant originals when possible" — does not mention the line-pattern rename pass that runs even with zero duplicates.

### Log experience

What's good:
- Each scope prints a header (`Scope: Line Patterns`), counts (`Scanned …`, `Duplicate groups found`), per-group breakdowns with names sorted alphabetically, and a summary block.
- Final per-scope timer line in the command (`CompactingStylesCommand.cs:48, 63, 78, 93`) is useful.

What's missing or noisy:
- **No structured separator between scopes in the visible log** beyond a blank line. Easy to lose your place when scrolling 4 scope outputs.
- **`Logger.Instance.LogWarning` does not surface in `LogView`.** All the catch blocks in `CompactionSharedHelper` (`CompactionSharedHelper.cs:44-46, 49-51, 132-143, 237-251, 294-305, 339-350, 376-388`) and `LinePatternCompactionService.IndexCategoryPattern` (line 640) write to `Logger.Instance.LogWarning` only — which feeds the file logger and structured logger, not the LogView. The user sees `Rewired from 'X': 12 references` but never sees "actually 3 of those failed silently". This is the single biggest log-quality gap.
- **Per-element rewire results not bucketed.** Every "Rewired from 'X': N reachable references" line gets printed. For a project with 200 duplicate groups × 5 candidates each = 1000 log lines. The summary is good but the body is spam.
- **No log of what got skipped vs what got blocked.** `BlockedDeletions` is just a count + list of names with no reason ("locked", "in use by group", "system family", etc.). The user has no path forward.
- **Inconsistent prefix conventions.** Line pattern logs `[LinePatternCompactionService]`, shared helper logs `[CompactionSharedHelper]`, but the `LogView` lines from the command itself have no prefix at all. Filtering or grepping the log is annoying.
- **`RevitCommandProgressReporter.LogWarning` and `LogError` both call `_log`** with no severity tag (`RevitCommandProgressReporter.cs:27-35`). Severity is erased before it reaches the UI.
- **No timing breakdown per group/per scope sub-step.** Only the wrapping `Stopwatch` at the command level. If a project is slow, you can't tell whether it's the index build, the rewire, or the delete pass.
- **Duplicate header lines.** Every service writes its own "Scope: …" + "Scanned …" + "Duplicate groups …" header (e.g. `LinePatternCompactionService.cs:39-41`), then the command writes its own "Line Patterns - Groups: …" summary line (`CompactingStylesCommand.cs:47`). Two almost-identical summaries per scope.

### Technical debt / bloat

- **2,681 lines across 6 files for a "find duplicates and dedupe" workflow** is a lot. The four services share a clear template (collect candidates → group by signature → build indexes → for each group: create canonical, rewire, mark for delete → finalize) but every implementation re-implements the loop from scratch. A `CompactionPipeline<TCandidate, TGroup, TResult>` base would shrink this by an estimated 40-50%.
- **Each service has an inner `XxxCandidate`, `XxxGroup`, and `XxxIndexes` private nested class** (e.g. `LinePatternCompactionService.cs:734-824`). Identical shape, different generic params. Prime template-method candidate.
- **Both `Compact` overloads everywhere.** The legacy `(Action, Action)` overload exists in every interface and implementation (`ILinePatternCompactionService.cs:10`, etc.) but only the `IProgressReporter` overload has any caller. `LegacyProgressReporter` is a dead-bridge adapter kept alive for these unused entry points.
- **`CompactingStylesContext` is in `LECG.Services` namespace but the file lives under `Services/PurgeAndCompaction/`** (`CompactingStylesContext.cs:7`) — namespace/folder mismatch, mild but present everywhere in this folder.
- **`InstanceElements` is permanently `Array.Empty<Element>()`** (`CompactingStylesContext.cs:82`) but it's still a public property. The `BuildParamIndex` still iterates it (`CompactingStylesContext.cs:179`). Dead surface — `IndexElements(instanceElements)` is a no-op call. Either delete the property or actually use it.
- **`SupportedViewTypes` HashSet** (`CompactingStylesContext.cs:11-23`) — hard-coded; if a project uses a view type not on the list (e.g. `ViewType.Schedule` for cell formatting, `ViewType.Walkthrough`), overrides on those views are silently un-rewired. No documentation of the rationale.
- **`IsExpectedXxxCompactionException` duplicated three times** (`LinePatternCompactionService.cs:692`, `FillPatternCompactionService.cs:559`, `TextStyleCompactionService.cs:233`) — same body, different name. Should be a single helper.
- **Stale comment in TextStyleCompactionService.** `// Step 3: Two-phase approach — rewire all groups, then single Regenerate + delete` (`TextStyleCompactionService.cs:66`) — there is no Regenerate.
- **Magic strings everywhere.** `"LECG-LP-"`, `"LECG-FP-"`, `"LECG-TT-"` const prefixes per service; format `:000` width; `GroupingToleranceMm = 1.0` only in line patterns. No central naming policy module beyond `LinePatternNamingPolicy`.
- **`PurgeContext.cs` exists in the same folder** alongside `CompactingStylesContext.cs` — two parallel "context" abstractions that don't talk to each other but cover overlapping document scans.
- **Result models are anaemic and inconsistent.** `LineStyleCompactionResult` has no `CanonicalCreated` (because line styles use survivor model, not create+rewire). `LinePatternCompactionResult` has `PatternsRenamed` while no other scope has a rename concept. No shared base interface (`ICompactionResult`?), so the command's summary block is hard-coded per scope.
- **`RevitCommandProgressReporter` collapses all severity** (see Log section). The whole `IProgressReporter` interface declares `LogWarning`/`LogError` for nothing.

### Architecture concerns

- **`Services/PurgeAndCompaction/` mixes two unrelated concerns.** The 30+ files in that folder span both Revit's "Purge Unused" pipeline (`PurgeService`, `DeepPurgeService`, `PurgeFillPatternService`, `PurgeLineStyleService`, etc.) and the dedup pipeline (`*CompactionService`). They share no code and no types. `PurgeFillPatternService` and `FillPatternCompactionService` both touch fill patterns but with completely separate logic. A user reading the folder has to mentally fork at every file. Splitting into `PurgeAndCompaction/Purge/` and `PurgeAndCompaction/Compaction/` would be free clarity.
- **Compaction services depend directly on `Logging.Logger.Instance`** (e.g. `CompactionSharedHelper.cs:407`, `LinePatternCompactionService.cs:640`). This bypasses the injected `IProgressReporter`. Two log sinks for one operation, one of which the user can't see.
- **No `ICompactionService` common interface.** Each per-scope service has its own interface despite identical contract shape (`Compact(doc, context, reporter) → result`). The command's `Execute` is four near-identical blocks because of this.
- **`CompactingStylesContext.Create` is called inside the transaction.** Building a 100MB parameter index inside a `Transaction.Start()/Commit()` window means the transaction is held open while you scan the model. For very large models this widens the window where a concurrent edit (worksharing) could conflict. Build the context outside the transaction; only the rewire/delete needs to be transactional.
- **No `CancellationToken` anywhere in the pipeline.** Modern async-style cancellation is impossible to bolt on without rewriting all four services.
- **Service registration is `AddSingleton`** (`Bootstrapper.cs:95-98`). These services are stateless and that's fine, but the command instantiates fresh `CompactingStylesContext` and `nextCanonicalIndex` per call so singleton vs scoped is moot — except that any future state on the service (caches, retry policies) would silently leak across documents.
- **`TextStyleCompactionService` writes `note.ChangeTypeId` directly without try/catch** (`TextStyleCompactionService.cs:314`). If one note throws, the whole rewire of the group aborts mid-stream, which then aborts the transaction commit, which in turn loses every prior compacted group in that scope (rolled back). One bad note = entire scope discarded.
- **No integration tests visible in this folder, only the commit log mentions formula auto-grouping tests.** Compaction is a destructive multi-API touch with no test scaffolding referenced.

## Recommended upgrade themes (top 5, ranked)

1. **Per-scope toggle dialog + dry-run / preview pane** — *S/M*. Reuse `PurgeView` pattern (a checkbox per scope + a "preview only" mode that runs the candidate-collection and group-build phases inside `RunRollbackOnly`). The user sees "Found X line-pattern groups, Y fill-pattern groups, Z text-style groups, W line-style groups — proceed?" before any write. Highest user-trust win for a destructive command. Also fixes the surprise of the line-pattern rename pass.
2. **Surface `Logger.LogWarning` to LogView + bucket per-element results** — *S*. Route the global logger through `IProgressReporter.LogWarning` so swallowed exceptions become visible. Replace the per-candidate `Rewired from 'X': N` spam with a per-group summary (`Group 17: 5 originals → 1 canonical, 412 references rewired, 0 deletions blocked`). Saves 80% of log volume and adds critical signal.
3. **Extract a `CompactionPipeline<TCandidate, TGroup, TResult>` base + single `ICompactionService` interface** — *M*. Each per-scope service collapses to a candidate collector + signature builder + index builder + canonical creator + rewire delegates. Removes ~1000 lines, makes the command's `Execute` a single loop over 4 services, makes future scopes (e.g. `MaterialCompactionService`) trivial. Also unifies the result model and stale `IsExpected…CompactionException` triplets.
4. **Build `CompactingStylesContext` once, outside transactions, and share across scopes** — *S*. Big perf win on large models, narrows the transactional window, removes the asymmetric "context built 4 times" pattern. While in there, fix `LineStyleCompactionService.RewireCurveElements` to use a pre-built curve→subcategory index (eliminate the per-original `FilteredElementCollector(doc).OfClass(typeof(CurveElement))` re-scan).
5. **Localization-safe text-style signature + cancellation token + completion summary** — *M*. Replace `LookupParameter("Horizontal Alignment")` with `BuiltInParameter` constants (verify which BIPs map; fall back to `null`-tagged signature so localized installs don't false-positive merge). Plumb `CancellationToken` through `IProgressReporter` (or a sibling param) and check it between groups. Add a final modal showing per-scope counts + an "Undo all 4 transactions" button (or restructure to one `Transaction` with `SubTransaction`s if Revit allows for this scope of work).

## Out-of-scope observations

- `WarningSwallower` is referenced in `TransactionService.RunWithWarningHandler` (`TransactionService.cs:96`) as the default — but `SafeFailureHandler` is a *safer* default (rolls back on errors instead of auto-deleting). The default in `RunWithWarningHandler` is the more dangerous one. Worth flipping at the framework level, not just in this command.
- `RevitCommandProgressReporter` (`src/Services/Infrastructure/RevitCommandProgressReporter.cs`) collapsing `LogWarning`/`LogError` into `Log` affects every command in the codebase, not just this one. Fix that and a lot of "where did the warning go?" questions across the addin disappear.
- `LogView` being `Topmost = true` (`RevitCommand.cs:80`) is a global UX decision that bites every long-running command; making it user-toggleable would help across the board.
- `LegacyProgressReporter` (`src/Services/Infrastructure/LegacyProgressReporter.cs`) is referenced by 23 services across the codebase. Killing the legacy `Compact(doc, context, Action<string>, Action<double,string>)` overloads here would only chip at the surface — a wider sweep is needed if the goal is to retire the legacy reporter pattern entirely.
- `PurgeContext.cs` and `CompactingStylesContext.cs` co-existing in the same folder, doing similar document-scan work without sharing code, is a microcosm of the broader Purge-vs-Compaction split. A unified `DocumentInventory` cache shared by both pipelines would amortize cost when (eventually) someone runs Purge then Compact in sequence.
