# Plugin Audit: Category Changer

## What it does (one paragraph)
The Category Changer lets a user pick one or more `FamilyInstance` elements in a Revit project, choose a target category from a searchable list, and have every distinct family behind those instances reassigned to that category. The "happy path" silently opens each `Family` in the family editor, sets `OwnerFamily.FamilyCategory`, and reloads it into the project. When Revit refuses the direct change (its so-called "Platform Limit" — typically 2D↔2D within mismatched templates), the command falls back to a "Creator Engine" / "Transplant" flow that creates a brand-new family from a built-in `.rft` template, nests the original family inside it as a sub-family, sets the target category on the wrapper, loads it into the project as `<OldName>-TRANSPLANTED`, then walks the project replacing every old `FamilyInstance` of point-based families with an instance of the new wrapper symbol and deleting the original. 2D↔3D conversions are explicitly blocked up-front.

It is not related to `TypeToLinkedModelsCommand` despite the similar-sounding name. That command exports types into separate `.rfa`/`.rvt` files and links them back; it shares zero infrastructure with Category Changer (different service `ILinkedModelExportService`, different base class `RevitCommand` instead of `ExternalEventCommand<>`, no overlap in helpers).

## Findings by axis

### Functionality
- **`SwapInstances` only handles `LocationPoint`** (`CategoryChangerCommand.cs:190-194`). Line-, curve-, hosted, and face-hosted instances are silently skipped with `[SKIP] Instance ... has no point-based location.` After a successful "transplant," any wall-hosted, line-based, or face-hosted family is left referencing the **old** family while the new `-TRANSPLANTED` family floats around in the project. The user sees `[SUCCESS]` for the family but the model isn't actually updated. This is the single biggest functional bug.
- **Transplant success is recorded even when `LoadFamily` returns null in pathological cases.** `RecreateAs` always returns the result of `targetDoc.LoadFamily(projectDoc, ...)` (`FamilyEditorService.cs:227`); if it returned `null`, the next line (`newFamily.Name = newName`) would NRE inside the rename transaction. There's no null-guard. The caller in the handler only counts success when `newFamily != null` (`CategoryChangerCommand.cs:117`), but the failure path just falls through (no `failCount++`, no log) — a silent drop.
- **`Family.LoadFamily(projectDoc, options)` overload returns void, not `Family`.** Line 227 reads `Family newFamily = targetDoc.LoadFamily(projectDoc, _loadOptionsFactory.Create());` — the actual return type of `Document.LoadFamily(Document, IFamilyLoadOptions)` is `bool` in some Revit versions and `Family` in others. Worth verifying against the targeted Revit API; if it currently compiles, fine, but it's a brittle use of overload resolution and worth pinning explicitly.
- **Annotation/2D conversions and 3D conversions are blocked at different layers.** The 2D↔3D guard lives in `ChangeCategory` (`FamilyEditorService.cs:34-39`) and throws an `InvalidOperationException` containing `"Platform Limit"`; the handler's `IsPlatformLimitException` (`CategoryChangerCommand.cs:251-255`) **only** triggers the transplant fallback when that exact substring appears. So genuinely transplantable 2D↔2D scenarios that Revit refuses internally won't enter the fallback at all — they'll be caught by `IsExpectedCategoryChangerException` and logged as `[ERROR]`. Conversely, the 2D→3D case explicitly blocked by `ChangeCategory` *would* trigger the transplant fallback because its message contains `"Platform Limit"`. That's the opposite of the intent commented in the source.
- **"Generic Model Bridge"** (`FamilyEditorService.cs:64-79`) — sets the family category to `OST_GenericModel`, then back to the target. If the second assignment fails after the first succeeded, the family is left as Generic Model and silently reloaded. The comment says "Try again after resetting to GM" but there is no rollback.
- **`BatchProcess`** (`FamilyEditorService.cs:244-255`) is unused. Comment admits "Future performance enhancement" — dead-but-public code.
- **Family-name suffix is hardcoded** as `-TRANSPLANTED` (`FamilyEditorService.cs:225`). Re-running on a previously transplanted family yields `XXX-TRANSPLANTED-TRANSPLANTED`. If the name already exists in the project, the rename will throw `ArgumentException` from Revit and the error path drops it.
- **Templates are searched in `English` / `Spanish` / `English-Imperial` only** (`FamilyEditorService.cs:313-318`). Non-English non-Spanish locales fail with the "Creator Engine Error" message even though Revit may have valid templates installed under the localized folder name.
- **No undo grouping.** Each call to `_transactionService.Run` is its own committed transaction (`Silent Family Edit`, `Nest Source Family`, `Set Category`, `Rename Transplanted Family`, `Swap Transplanted Instances`). On a failure halfway through the transplant, the project is left with leftover families and no obvious way for the user to roll back.
- **Selection seeding ignores the current view's link selections.** `SelectionSeedHelper.GetSelectedReferences` only walks `uiDoc.Selection.GetElementIds()`; selecting via the project browser or in a linked model doesn't seed.

### Error handling
- **"Catch the world if it looks expected" is the dominant pattern.** `IsExpectedCategoryChangerException` lumps together `ArgumentException`, `InvalidOperationException`, `RevitExceptions.InvalidOperationException`. That swallows e.g. `Autodesk.Revit.Exceptions.ArgumentException`, `Autodesk.Revit.Exceptions.OperationCanceledException`, `ApplicationException` — none of which are caught here, so they bubble to `RevitCommand.Execute` and hit the generic error window. That's actually OK behavior, but it means the handler's "guarded" claim is misleading.
- **Transplant failure handler only catches the inner branch but not its enclosing exception variable.** `CategoryChangerCommand.cs:126-130` — when the transplant throws something matching `IsExpectedCategoryChangerException`, the user sees `[TRANSPLANT FAILED] {transplantEx.Message}`. But anything else (e.g., `IOException`, `UnauthorizedAccessException` from temp-file write) propagates to the outer try, gets caught by the *outer* expected filter, and is logged as `[FATAL ERROR]` instead of attributing it to the transplant. Confusing for the user.
- **`ProcessFamily` swallows everything to `false`** (`FamilyEditorService.cs:136-140`) and logs a generic `[ERROR] {ex.Message}` to `Logger.Instance` — but the *caller* in the handler also wants to know whether to attempt the transplant fallback. Because `ProcessFamily` returns `false` instead of throwing, the handler sees `success == false` (`CategoryChangerCommand.cs:103`) and logs `[FAILED]` with no fallback. The pre-check at `FamilyEditorService.cs:30-39` exists *specifically* to dodge this swallow — comment confirms: "to ensure the exception reaches the caller (Command) instead of being swallowed by ProcessFamily's log-and-return-false." That's a strong code smell: control flow is being routed around the service's own design.
- **`SwapInstances` has no transaction-failure path.** If the transaction itself throws (e.g., another modeless command holding the doc), the user never sees a message — `_transactionService.Run` is invoked outside any try/catch in `CategoryChangerCommand.cs:182-241`.
- **`TryDeleteTemporaryFile`** (`FamilyEditorService.cs:289-306`) silently swallows `IOException` / `UnauthorizedAccessException`. Acceptable for cleanup, but no warning is logged — temp files accumulate in `%TEMP%` over time.
- **External-event `Execute` outer catch** wraps the entire loop in one try (`CategoryChangerCommand.cs:73-155`); a single bad family in the middle short-circuits the rest. Per-family inner try exists (`:84-143`), but its filter is the same narrow set, so an unexpected exception from the 5th of 50 families aborts the remaining 45.

### Performance
- **`SwapInstances` does a full unfiltered `FilteredElementCollector.OfClass(typeof(FamilySymbol))`** then a separate `OfClass(typeof(FamilyInstance))` (`CategoryChangerCommand.cs:166-178`), once per transplanted family. With N transplanted families, that's 2N collectors over the entire project. For a project with thousands of family instances this is wasteful — should collect once and group by `Family.Id`.
- **`ChangeCategory` is the only per-family work mode.** It opens, edits, closes, and reloads the family document one at a time inside `ProcessFamily` (`FamilyEditorService.cs:108-145`). For 50 families that's 50 round-trips through `EditFamily`/`LoadFamily`. The `BatchProcess` API exists but is never wired up.
- **`RecreateAs` writes to `%TEMP%`, opens a new family doc, runs three transactions, and reloads.** It's expensive per family. No batching, no caching of templates (the path is re-resolved each call by enumerating filesystem dirs).
- **Category list rebuilt on every keystroke.** `OnSearchTextChanged` allocates a brand new `ObservableCollection<Category>` (`CategoryChangerViewModel.cs:90-101`), forcing the ListBox to fully rebind. For a few hundred categories it's negligible, but the right pattern is to use a `CollectionViewSource` filter.
- **`AnyFamilyInstanceFilter` is wide open** — preselecting hundreds of irrelevant elements gets through. The stricter `FamilyInstanceFilter` (which checks `FAMILY_WORK_PLANE_BASED` and `FamilySelectionPolicy.IsSafeToConvert`) exists in the same file but isn't used by Category Changer.

### UX / UI
- **Modeless dialog with no progress/spinner inside the dialog itself.** Once the user clicks Execute, the work happens in the external event and the only visual feedback is the separate Log window popped open by `OnShowLog` (`CategoryChangerCommand.cs:75`). The Execute button stays enabled, the dialog closes when work finishes (`CloseAction` at `:150`). On long runs the user has no progress bar, no per-family progress, no "running…" state.
- **"Cancel" button has no contract during execution.** Pressing Cancel during a transplant won't stop the loop; nothing checks a cancellation token.
- **Title says `"CATEGORY CHANGER [V6-EVENT]"`** (`CategoryChangerViewModel.cs:39`). That's a developer-facing build/version label leaking into end-user UI.
- **Category picker is a flat alphabetical list** (`CategoryUtils.cs:30`) with no grouping (Model vs Annotation), no icons, no indication of category type, no count of how many of the user's current selection are *already* in that category. For users with hundreds of categories the search box is the only navigation aid.
- **No preview / dry-run / impact statement.** A user transplanting a family with 200 instances will only learn after the fact via the log. There's no "this will replace 200 instances of XYZ — proceed?" confirmation.
- **No conflict warning when target = current category.** Clicking Execute on a family already in the chosen category still runs through `EditFamily` / `LoadFamily`. Wasted I/O and a misleading `[SUCCESS]`.
- **Selection control is the shared `SelectionViewModel`** (`CategoryChangerViewModel.cs:26`). Good consistency — but the dialog never re-validates that selected refs are still valid after Revit selection state changes.
- **The view sets `WindowIcon` to `Icons.Category`** (`CategoryChangerView.xaml:6`) — fine, but no visual distinction between "direct change" and "transplant" outcomes; both are buried in log text.

### Log experience
- **Two parallel logging stacks.** The handler logs through `_viewModel.OnLog?.Invoke(...)` (which routes to `RevitCommand.Log` → `Logger.Instance.Log`). The service `FamilyEditorService` logs directly through `LECG.Services.Logging.Logger.Instance.Log`/`LogWarning`. The VM also logs directly in `Apply`'s catch (`CategoryChangerViewModel.cs:63`). Three call paths into the same logger — one of them (the service) bypasses the per-command `Log` wrapper entirely.
- **Inconsistent prefix taxonomy.** Tags used: `[SUCCESS]`, `[FAILED]`, `[ERROR]`, `[TRANSPLANTING]`, `[TRANSPLANT FAILED]`, `[SWAPPING]`, `[SKIP]`, `[WARN]`, `[FATAL ERROR]`. No level convention, no machine-parseable structure, varying indent (`  `, `    `, none).
- **No timing data.** Despite the log being the *only* user feedback, there's no per-family elapsed time, no total wall time, no count of skipped non-point instances broken out from real failures.
- **No structured (`Microsoft.Extensions.Logging`) logging.** `RevitCommand.Execute` resolves an `ILoggerFactory` for command-level logs (`RevitCommand.cs:39-49`), but the handler runs *inside* the external event after that scope is set up — and the handler doesn't reuse the structured logger. So Category Changer's per-family work is invisible to any external log sink.
- **The fatal-error catch silently swallows non-VM-context exceptions.** `Apply`'s catch (`CategoryChangerViewModel.cs:61-64`) writes "Error in CategoryChanger Apply" to the global logger but the user, looking at the per-command log window, sees nothing because no `OnLog` callback is invoked from there.
- **Log window can outlive the dialog**, since the dialog `CloseAction` is invoked at handler completion (`CategoryChangerCommand.cs:150`) but the log window manages its own lifetime via `RevitCommand._logWindow`. That's fine, but there's no completion banner or "Close" affordance specific to Category Changer.

### Technical debt / bloat
- **God-handler.** `CategoryChangerEventHandler` (200 LOC in the same file as the command) holds: dependency wiring (`Initialize`), the per-family loop, fallback orchestration, the entire `SwapInstances` Revit-mutating method, and exception filters. `SwapInstances` is *the* place where instance replacement belongs and it has no service abstraction whatsoever. It also depends on `ITransactionService` directly, which the command had to thread through to the handler.
- **Two layers of "expected exception" filters** (`IsExpectedCategoryChangerException` in command, `IsExpectedFamilyEditorException` in service, plus `IsExpectedFamilyNestingException`). They overlap, none are justified by a comment, and each new exception type requires hunting through both.
- **The "pre-check before service call" pattern at `FamilyEditorService.cs:24-39`** documents the leak: the service's swallow-and-return-false design forced the caller to duplicate logic so the right exception could escape. Either `ProcessFamily` should `throw` (and let the handler decide), or the `ChangeCategory` API should return a richer result type than `bool`.
- **Magic strings.** `"Platform Limit"` is the substring used to drive control flow (`CategoryChangerCommand.cs:254`). A typo in the service breaks the handler with no compiler help.
- **Duplicated category-detection logic.** `IsModelCategory` lives in `FamilyEditorService` (`:89-106`) as a private method, and `CategoryUtils.GetValidFamilyCategories` does its own `CategoryType.Model | Annotation` filter. The two definitions could disagree (and almost do — `IsModelCategory` whitelists by `BuiltInCategory`, `CategoryUtils` by `CategoryType`).
- **`BatchProcess` is dead code.** Documented as future-only, no consumers.
- **`FamilyInstanceFilter` (the strict one) is dead-ish here.** Used elsewhere but not by Category Changer, where `AnyFamilyInstanceFilter` is preferred — meaning the safety policy `FamilySelectionPolicy.IsSafeToConvert` does not protect this command's flow.
- **`Title = "CATEGORY CHANGER [V6-EVENT]"`** is a stale dev tag (`CategoryChangerViewModel.cs:39`).
- **Comment artifacts:** `// Optional: Swap instances in project` (`:121`), `// This is the key: ...` (`:36`), `// Note: sourceDoc was closed earlier in the try block to avoid lock` (`FamilyEditorService.cs:239`) — narrative-style comments compensating for unclear flow.
- **`RaiseExternalEvent` static state.** `ExternalEventCommand` holds one static `_externalEvent` per closed generic; if the command is invoked, the dialog dismissed, and re-invoked, the static handler is re-`Initialize`'d each time. It works, but is brittle (e.g., if a previous run is still pending, raising again silently coalesces).

### Architecture concerns
- **Service boundary is leaky.** `ChangeCategory` mixes "decide whether to allow this" (the 2D/3D guard) with "execute it." The decision could live in a small policy type, with the service purely doing the mutation. As-is, the command duplicates parts of the policy via the `IsPlatformLimitException` / message-substring check.
- **Two service abstractions confused.** `IFamilyEditorService` is named for "family editor" but `RecreateAs` is really a *family-conversion* concern (note the namespace `LECG.Services.FamilyConversion` already hints at this). Splitting into `IFamilyCategoryService` (in-place change) and `IFamilyTransplantService` (recreate + nest) would reduce the surface and make the handler cleaner.
- **Instance swapping has no service.** It's a generic operation (swap all instances of family A with family B, preserving location/rotation/level/host) that other commands could use. Lives inline.
- **VM has Revit DB types as public members.** `Doc`, `SelectedRefs`, `SelectedCategory`, `FamilyService` are all surfaced (`CategoryChangerViewModel.cs:27-32`). The handler reaches in and reads them. Tight coupling — the VM is functioning as a parameter struct, not a view model.
- **`OnLog`/`OnShowLog`/`RequestRun`/`CloseAction` are `Action` properties on the VM**, set by the command before showing the view. This is a callback-spaghetti workaround for the fact that the VM can't talk to the external-event subsystem directly. A small `ICategoryChangerSession` interface would replace four delegates and document the contract.
- **Modeless + external event flow is correct in shape, but execution proceeds with no synchronization between the dialog and the handler.** The user could in principle dismiss the dialog, click Execute on another command, etc., while the handler is mid-loop. There's no busy state.
- **DI lifetimes are inconsistent.** `IFamilyEditorService` is singleton (`Bootstrapper.cs:205`), but it captures no state, so that's fine; meanwhile every call to `EditFamily` / `LoadFamily` is per-document, and the singleton pattern implicitly assumes thread/document agnosticism. Worth documenting.

## Recommended upgrade themes (top 5, ranked)

1. **Fix transplant instance-swapping for non-point hosts (CRITICAL).** `SwapInstances` skips line-based, hosted, face-hosted, and curve-driven instances. After a transplant, those are silently orphaned. Build a proper instance-replacement routine (or a service) that handles the common host types: point, line, face/host, curve-driven. **Effort: M.** Why first: this turns silent data corruption into a fixable bug.

2. **Replace bool-return + string-substring control flow with a typed result.** Have `ChangeCategory` return e.g. `CategoryChangeResult { Status, Reason, RequiresTransplant }` (or throw a dedicated `CategoryChangeBlockedException`). Eliminates `IsPlatformLimitException` / "Platform Limit" magic string, removes the duplicated 2D/3D pre-check, and lets `ProcessFamily` either succeed, fail-with-reason, or surface "needs transplant" cleanly. **Effort: S–M.** Why: every other improvement gets cleaner once the contract is honest.

3. **Extract instance swap, transplant, and policy into dedicated services.** Move `SwapInstances` out of the handler into `IFamilyInstanceSwapService`; split `IFamilyEditorService` into `IFamilyCategoryService` (in-place) and `IFamilyTransplantService` (recreate). Handler shrinks to ~50 LOC of orchestration. **Effort: M.** Why: the current 200-LOC handler is the single biggest source of technical debt and blocks unit testing.

4. **Real progress + cancellation in the dialog.** Use the existing `RevitCommandProgressReporter` pattern (already used by `TypeToLinkedModelsCommand` at `:65`). Show a per-family progress bar inside the dialog, disable Execute during run, surface success/fail counts in the dialog itself, allow cancellation between families. **Effort: M.** Why: the only feedback today is a separate log window with inconsistent prefixes; a long batch is opaque to users.

5. **Structured logging + log taxonomy + timing.** Standardize tags, route through `Microsoft.Extensions.Logging` (already wired into `RevitCommand`), include per-family elapsed time and instance counts, and emit a single end-of-run summary that distinguishes "skipped (host type unsupported)" from "failed (Revit refused)". **Effort: S.** Why: small change, big jump in diagnosability for an operation that frequently fails for legitimate Revit reasons.

## Out-of-scope observations

- **`ExternalEventCommand<THandler>` static state** (`Core/ExternalEventCommand.cs:9-10`) — one static event per closed generic across the whole AppDomain. Re-`Initialize` on every command invocation means a previous in-flight run can be clobbered. Not Category-Changer-specific but bites here first because Category Changer is the only handler that maintains stateful callbacks (`OnLog`, `CloseAction`). Worth reviewing the lifecycle for all `ExternalEventCommand`-derived commands.
- **`Logger.Instance` singleton** is set up by `RevitCommand.PrepareCommandExecution` (`RevitCommand.cs:118-125`) and shared globally. Two simultaneous external-event-driven commands would interleave their log lines. Not currently exploitable but the design assumes one command at a time.
- **`SelectionSeedHelper` is `internal`** (`Core/SelectionSeedHelper.cs:9`) — fine, but consumed in 10 commands. Convert to a service to enable testing.
- **`Document.LoadFamily` overload chosen at `FamilyEditorService.cs:227`** returns different things across Revit API versions. Worth adding a wrapper in the project's Revit-compat layer.
- **`docs/review/revit-api/*.jsonl` files** are huge generated API dumps committed to the repo (visible via Grep hits). Out of scope for Category Changer but they bloat search and clones.
- **The shared `SelectionViewModel`/`SelectionControl` component is solid** and correctly reused here. Good piece of infrastructure that other commands also benefit from.
- **The 2D/3D template fallback in `FindTemplate`** depends on filesystem layout under the Revit install dir. Locales beyond English/Spanish (`FamilyEditorService.cs:313-318`) are not handled — broader localization story for the addin.

## What's actually good

- The external-event pattern is correctly used (Revit API context vs WPF UI context).
- The 2D↔3D pre-check exists and prevents the worst-case "create totally broken family" scenario.
- The transplant flow is a creative workaround for a real Revit limitation, and the temp-file cleanup is at least guarded.
- Category list correctly excludes `Internal` categories via `CategoryType.Model | Annotation`.
- DI wiring is consistent with the rest of the codebase (singleton service, transient VM).
- Preselection seeding is a nice touch — users with elements already selected don't have to pick again.
- The `LecgWindow` base, `SelectionControl` component, and `LecgTheme.xaml` give the dialog a consistent look with the rest of the addin.
